Case Study 03 · LettrLabs Design System
AI-ready system

Building a design system a person and an AI can both design from.

I owned LettrLabs' design system—tokens, components, documentation, and the tooling around it. The goal was not just consistency for designers. It was to make the system explicit enough that an AI model could produce on-brand work too: write the copy, follow the recipes, and get audited against the same rules a designer would.

See the map case study → This system is the foundation the map redesign and the Codex prototype were built on.

Executive summary

I standardized every component on shared variables, documented the system in machine-readable form, encoded UX copy into reusable formulas, and built an audit that classifies any new design's issues automatically. The result: designers and AI produce work that already fits the system—and design review becomes a rule-check instead of an opinion.

Why this mattered

A system is only as good as its consistency—and ours lived in people's heads.

The UI had drifted. Bootstrap-era hex codes, off-scale spacing values, a button labeled "Clicked" where the system said "Pressed," and the same component rebuilt five slightly different ways. Copy was inconsistent too—every error, empty state, and warning was written from scratch, in a slightly different voice.

As we started using AI to design and prototype, the deeper problem surfaced: nothing was written down in a way a model could follow. The system was tribal knowledge, so no AI—and no new designer—could produce on-brand work without a senior reviewer in the loop.

So I set a clear bar: make the system explicit enough that a person or an AI, given the same task, arrives at the same answer.

Architecture

Consistency first, then structure everything on tokens.

Before designing new screens, I made every component resolve to shared variables. Tokens are layered so meaning—not raw values—drives the UI, and named by a single rule: category, role, intensity.

Layer 01 Primitive The raw values—every color, size, and radius the brand owns, with no meaning attached yet.
→
Layer 02 Semantic Roles map to primitives—brand/bg/default, neutral/text-icon/strong—so intent stays stable even if a value changes.
→
Layer 03 Component Each recipe consumes semantic tokens, so a Button or Toast is never bound to a raw hex or pixel.
BrandReserved for the user's positive action
NeutralText, icons, surfaces, borders
InfoSelection and information—blue, not brand
SuccessConfirmed and completed states
WarningCaution without failure
ErrorBlocking failures only
SpecialVariable images / mail merge only
Dimension scales are not interchangeable. Spacing, padding, gap, control gap, radius, border, height, wrapper width, opacity, and icon size are separate scales—each used only where it belongs.
Focus is a 4px halo, no exceptions. One focus treatment across every control, so the system reads as one product.
Typography stays disciplined. 11 text styles, sentence case only, nothing under 12px, and no all-caps titles.
Disabled uses lighter tokens, not opacity. And selection is info-blue, not brand—brand is saved for the primary action.
Tooling

I built a Figma tool so the system checks itself.

A system drifts the moment someone reaches for an outdated variable. So I built a small Figma tool that flags when a layer is bound to a stale token, and organized every component by category so the right building block is easy to find.

That turned consistency from a manual review someone has to remember into something the file surfaces on its own—which is exactly what makes the rest of the system safe to automate.

The AI-ready layer

I made the system machine-readable, not just human-readable.

Once components were consistent, I used AI to draft each one's definition—its purpose, and where it should and should not be used—then layered structured documentation so a model could reason about the system as reliably as a designer.

01

UX copy guide

Voice and tone encoded as formulas—state, error, warning, success, validation—each a fill-in pattern with real LettrLabs examples. AI and designers both generate copy that already sounds like the product, with no rewrite pass.

02

Component specs

Every component documented—shared styling, the CSS for the ones that need it, and explicit do's and don'ts—so reuse and implementation follow one source of truth instead of tribal knowledge.

03

QA & audit rules

A reference set of patterns, common violations, and known deviations. Any new design is audited against it, so problems surface as rule-breaks rather than opinions.

UX copy system

Copy became a formula, not a guess.

Each message type has a pattern grounded in NN/g principles: say what happened, what it means, then what to do next—blame the system for failures, never the user. Give the model the state, and it fills the formula.

System failure — formulaWe couldn't [action]. [Next step]. If the problem continues, [fallback].
On-brand output

"We couldn't remove this location. Try again. If the problem continues, refresh the map and try once more."

Validation — formula[Item] is required to continue. [Action] to proceed.
On-brand output

"A template is required. Select a template to continue."

Warning — formula[Issue]. You can still continue, but [impact]. [Recommendation].
On-brand output

"Holdout testing is enabled. You can still continue, but your budget may need to be higher for reliable measurement."

Success — formula[Action] successful. [Optional next step].
On-brand output

"Location added successfully."

Automated QA

The audit sorts every issue into one of three buckets—because each needs a different fix.

Instead of "this looks a bit off," the audit is surgical. Point it at a Figma screen and it returns a structured report that the team can act on directly, before anything reaches engineering.

Violation

Fix the design

The design contradicts a documented rule.

e.g. a button labeled "Clicked" instead of "Pressed," or a disabled state rendered at opacity 0.5 instead of the muted token.

Deviation

Fix the binding

The value is right, but it isn't bound to a token—or it's the right token in the wrong place.

e.g. a raw #5551FF fill where brand/bg/default should be bound.

New pattern

Have the conversation

The design introduces something the system doesn't document yet. Not a bug—a proposal.

e.g. a hover-preview variant of Toggle Card. Name it and add it, or replace it with an existing recipe.

How AI operates the system

Four places the system does the work.

Because the rules are explicit and machine-readable, AI isn't guessing at the brand—it's executing a system I defined.

Writes definitionsAI drafted each component's purpose and its where-to-use / where-not-to-use guidance, which I reviewed and tightened.
Generates copyThe encoded formulas let AI produce on-brand microcopy for any state on demand, in the product's voice.
Audits designsThe QA rules let AI review a screen before handoff and return violations, deviations, and new patterns.
Powers prototypesThrough Figma Code Connect, Storybook, and the Claude Design System, an AI-built prototype inherits the real components, states, and copy.
Impact

One source of truth that people and models both build from.

Product outcome

The map redesign reused and extended the system instead of inventing one-off UI, so new work inherited consistency by default.

Prototype outcome

Because the Codex prototype pulled real components, states, and copy through Code Connect and Storybook, it behaved like the product—not a mock.

Process outcome

Design review shifted from opinion to rule-check. Issues get caught—and classified—before engineering ever sees the file.

Scale outcome

The system set the foundation for consistent, AI-assisted design as the team and surface area grew, with new patterns surfaced as proposals rather than accidents.

What's next

The audit already tells me where the system needs to grow.

Because every new pattern gets surfaced instead of silently absorbed, the system flags its own gaps—shadow tokens, a code-editor pattern, letter-preview ink, and print bleed/safe zones are all candidates the audit raises as proposals rather than bugs.

Next, I'd expand Figma Code Connect coverage so more of the system is directly prototype-ready, and measure how much faster an on-brand screen ships once a designer—or a model—can lean on the rules instead of rebuilding them.

"A design system earns its keep when the same rules produce the same answer—whether a designer or a model is doing the work."
