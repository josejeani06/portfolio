Process

The first design was far more powerful

To connect a CRM like Salesforce, you’d browse the entire schema, hand-map every object and field to the attribution model, define conversion / lead / exclude rules, then run a full extract-and-load pipeline into SQL. It could model almost anything. And that was exactly the problem. 3 in 10 users stalled before finishing.

Ivan JoseIntegration Framework

Process

The least clever version held up

You connect with credentials, and attribution becomes its own explicit step. You confirm which statuses count as a Lead, a Conversion, or Job Complete, and a live warning fires if the choice would attribute nothing.

That’s the through-line of the whole project. The reusable pattern is what’s left after deciding what the user should never have to care about.

Decisions

Three calls, written down

QuestionTrade-offDecision
How much should connect ask for up front?Exposing every object and field was powerful, but it turned setup into a data-engineering task.Cut connect down to the few required inputs: name, Client ID, and a masked secret, all tested before anything saves.
Connect and attribution, one flow or two?One flow felt continuous, but attribution carries different business logic and risk than authentication.Split them. Connect stays lightweight and works the same everywhere; attribution is shown only to the users who need it.
Custom connectors, or one reusable shell?Custom screens fit each API perfectly, but every new app restarted design and engineering. That was 6 one-off builds at 3 to 4 weeks each.One reusable lifecycle, where the connector-specific parts are configuration.
